# MAX: подготовленная серверная граница

Статус на 14 ноября 2026: **отключено**. Подготовлены адаптер, контракт хранения и локальные проверки; настоящий бот, профиль организации, секреты, webhook, база подписок и очередь не подключены. Публичного адреса и QR-кода пока нет. Никакие личные сообщения из этого кода при импорте или проверке не отправляются. Сайт и его Worker не изменяются этим модулем.

## Что получит пользователь после подключения

Один бот сервиса обслуживает личные диалоги разных пользователей. После привязки своего кабинета пользователь получает выбранные события: перебитая ставка, новая ставка на его лот, скорое завершение/результат торгов, подходящий новый лот, снижение цены и изменение состояния кабинета. Изменяемый баланс браузера и демонстрационные ставки не создают доверенные события для рассылки.

Команды `/bids`, `/lots`, `/subscriptions` читают только подтверждённую сервером привязку; `/stop` отключает уведомления; `/help` объясняет команды. Провайдерная граница сейчас формирует количество элементов и ссылку на сайт; подробное представление ставок/лотов добавляется при подключении реального серверного кабинета. Бот не делает ставки, не меняет объявления и не проводит оплату. Неизвестные команды показывают справку.

## Официальные особенности MAX

Для создания бота нужен верифицированный профиль организации, ИП или самозанятого и модерация. Публичное имя выдаёт сама платформа: нельзя считать желаемое имя или ссылку уже занятой нами. Отображаемое название настраивается отдельно. Это отличается от регистрации Telegram-бота через BotFather. [Создание и модерация MAX-бота](https://dev.max.ru/docs/chatbots/bots-create/create).

Текущий API использует `https://platform-api2.max.ru` и токен в заголовке `Authorization`; токен не помещается в URL. Webhook проверяется по `X-Max-Bot-Api-Secret`, переданному при создании подписки. Внешний webhook должен работать по HTTPS/443 с доверенной TLS-цепочкой. Официальная документация отдельно указывает требования к сертификатам: их должен проверить оператор инфраструктуры; отключать проверку сертификатов нельзя. [API](https://dev.max.ru/docs-api), [подписка webhook](https://dev.max.ru/docs-api/methods/POST/subscriptions), [отправка сообщений](https://dev.max.ru/docs-api/methods/POST/messages).

## Файлы и запуск проверок

- `integrations/max/adapter.cjs`: чистая серверная граница, не HTTP-приложение.
- `integrations/max/config.example.json`: конфигурация с `state: disabled`, без секретов и выдуманного адреса бота.
- `integrations/max/adapter.test.cjs`: проверки с памятью вместо БД и заглушкой транспорта; внешней сети нет.

```sh
node integrations/max/adapter.test.cjs
```

Проверены отключение по умолчанию, доверенный вход при привязке, хеш одноразового кода, отдельное подтверждение в кабинете, повтор/подмена входящих событий, чужие идентификаторы, команды из проверенного inbox, фильтры, тихие часы, исключение закрытых данных из сообщений, версия привязки и запрет слепого повтора неопределённой отправки. Один локальный файл тестов проходит; это не тест живого MAX или реальной распределённой БД.

## Подключение

1. Владелец регистрирует/верифицирует свой профиль в MAX для бизнеса и создаёт бота с отображаемым именем «Фаст Торги» либо официальным брендом «ФАС торги».
2. Используется исходная графика сайта: `dist/assets/brand/fas-torgi-logo.png`, квадратный вариант — `dist/assets/app/icon-512.png`. Платформа предоставляет кадрирование под требования к аватару; новая эмблема не придумывается. Требования размера сверяются в кабинете MAX при загрузке.
3. После модерации реальная ссылка сохраняется в `botUrl`. Только после проверки этой ссылки можно выпускать QR-код. Секреты `MAX_BOT_TOKEN` и `MAX_WEBHOOK_SECRET` задаются через закрытые настройки сервера, не в браузере, Git, журнале или чате. Для webhook здесь требуется случайный секрет минимум 32 символа из разрешённого MAX набора.
4. Реализуются защищённые серверные аккаунты, авторизация `authorizeAccount`, транзакционный репозиторий ниже и постоянная очередь с лимитами. Локальный профиль демосайта не заменяет серверную личность.
5. HTTPS webhook вызывает `handleWebhook` с исходным телом и заголовками. Ответ HTTP 200 разрешён только после результата `accepted: true`; ошибка БД должна сохранить возможность повторной доставки. Секрет проверяется до JSON и работы с хранилищем; тело ограничено 64 КиБ. Обработчик framework также должен ограничивать размер до чтения полного тела.
6. Создаётся подписка MAX на `bot_started`, `bot_stopped`, `dialog_removed`, `message_created` с секретом. Этот модуль сам не вызывает административный `POST /subscriptions` и не меняет профиль бота.
7. На стенде проверяются собственный/чужой кабинет, утечка ссылки, просроченная привязка, повтор webhook, отключение, обновление подписок, лимиты, перезапуск воркера и неопределённая отправка.
8. После проверки схемы и серверных контрактов указывается `state: ready` и реальный `reviewReference`. Даже тогда `status()` сообщает `configured-not-probed`, а не выдуманную успешную связь. Сетевой транспорт вызывается только явным `deliver` из доверенной очереди.

## Привязка в два шага

`beginLink(authenticatedContext)` получает `principalId` только через серверный `authorizeAccount(context, 'link_max')`. Контекст должен подтверждать действительную сессию и защиту от CSRF. Создаётся случайный код 32 байта, срок 10 минут; в БД сохраняется только SHA-256 кода. Результат содержит настоящую ссылку MAX с `start`, но не токен бота.

Событие `bot_started` лишь добавляет **предварительного** кандидата MAX к заявке. Сама ссылка не активирует доступ к аккаунту. Пользователь возвращается в свой авторизованный кабинет, проверяет привязываемого получателя и явно подтверждает через `confirmLink(context, linkId)`. Репозиторий атомарно проверяет владельца, срок, отсутствие повторного использования и конфликта уже занятой MAX-личности. Перепривязка не должна молча перезаписывать другой аккаунт; предыдущие очереди теряют право отправки после увеличения версии привязки.

MAX-идентификаторы хранятся десятичными строками. Числа вне точности JavaScript отклоняются, а не округляются. Каналы и групповые сообщения не допускаются в личный командный путь. Официальные события/поля: [Update](https://dev.max.ru/docs-api/objects/Update).

## Контракт репозитория

Репозиторий внедряется сервером, а не браузером. Его методы — обязательная граница безопасности; подмена на простой Map в production недопустима.

| Метод | Обязательные гарантии |
| --- | --- |
| `savePendingLink(record)` | Уникальный `nonceHash`, владелец, срок; сырой код не сохраняется. |
| `applyInboundUpdate(record)` | Атомарный постоянный inbox по `eventKey`; возвращает `{durable:true}` только после записи. `bot_started` однократно прикрепляет кандидата к ещё действующей заявке, без активации. Stop/remove отключает только совпадающие `maxUserId` и `chatId`; старое событие до времени активации не выключает новую привязку. |
| `confirmPendingBinding(request)` | Серверный владелец, явное подтверждение, заявка не просрочена/не использована, MAX-личность не занята другим владельцем. Возвращает активную opt-in привязку с возрастающей версией. |
| `getVerifiedInboundUpdate({eventKey})` | Только сохранённая после аутентификации webhook запись; `verified:true`, исходный ключ и нормализованная команда. Для команды также возвращаются серверные `bindingId`/`bindingVersion` на момент приёма. Идентификаторы команды никогда не читаются из параметров публичного браузерного запроса. |
| `getBindingForMaxIdentity(identity)` | Совпадающая пара MAX user/dialog; активная запись с `principalId`, `provider:'max'`, `optedIn:true`, `version`, настройками. |
| `getAccountView({principalId,kind,limit})` | Авторизованный серверный срез только этого владельца; без платёжных секретов и персональных документов. |
| `stopBinding(request)` | Атомарное отключение указанной версии, отзыв очереди; не затрагивает чужую привязку. |
| `getAuthorizedEvent({eventId,principalId})` | Событие из доверенного серверного журнала; авторизованный получатель, актуальные разрешённые поля лота. В текст отправляются фиксированное событие, номер и цена лота; произвольные name/city не пересылаются. Не принимает готовый текст или событие из localStorage. |
| `getBindingByPrincipal(request)` | Последняя opt-in версия только этого владельца/провайдера. |
| `claimDelivery(request)` | Уникальный lease по событию/привязке/версии, постоянное состояние `claimed/sent/busy/unknown/deferred/cancelled`, атомарный лимит канала/всего бота. |
| `deliveryStillAllowed(context)` | Последняя проверка владельца, версии, opt-in, разрешённого события, актуальных фильтров, тихих часов и лимита непосредственно перед отправкой. При отказе возвращает false; адаптер терминально отменяет lease через `cancelDelivery`. |
| `cancelDelivery(context)` | Атомарно отменяет только свой lease после отказа финальной проверки. |
| `deferDelivery(context)` | Атомарно переносит только свой lease в постоянную очередь тихих часов; не перезаписывает sent/unknown. |
| `markSent(context)` | Подтверждение серверного ID сообщения и времени, только для своего lease. |
| `markUnknown(context)` | Фиксирует неопределённый исход, запрещает автоматический повтор до отдельной сверки. |

Inbox команды сохраняет серверный снимок `bindingId`/`bindingVersion` в момент приёма. `readCommand` отвергает несовпадающую версию и событие раньше `activatedAt`, поэтому старый `/stop` не отключает новый сеанс после перепривязки.

Вызов `readCommand(eventKey)` разрешён только из доверенного обработчика inbox. Он сам загружает проверенные идентификаторы и ещё раз сверяет текущую привязку; передать произвольные `userId/chatId` вместо ключа нельзя. Результат команды — разрешённый ответ для общей очереди, не непосредственная отправка. Публичного маршрута для вызова этих методов сейчас нет.

## Подписки и очередь

Формат настроек совпадает по смыслу с Telegram: `version:1`, `events`, `categories`, `regionCodes`, `minPriceKopecks`, `maxPriceKopecks`, `frequency: instant|hourly|daily`, `quietHours` с IANA-зоной и минутами начала/окончания. Пустой набор категорий/регионов означает отсутствие соответствующего ограничения. Пустой `events` отключает все события. Равные границы включённых тихих часов означают тишину на весь день.

Цена — целое количество копеек в десятичной строке; границы проверяются без плавающей точки. Фильтры категории/региона/цены применяются к `matchingNew`/`priceDrop`. Выбранные личные события вроде перебитой ставки не теряются из-за поискового фильтра другой категории. Настройки нужно сохранять только после проверки серверной сессии; отдельного изменяющего настройки маршрута в этом модуле нет.

`hourly` и `daily` задают минимальный интервал; постоянный внешний outbox должен удерживать и затем собирать ожидающие события в дайджест. Тихие часы проверяются после атомарного claim, возвращают `deferred` и сохраняют только свой lease через `deferDelivery`; уже подтверждённый sent не перезаписывается. Здесь нет таймера, cron или самопроизвольного прогона. Известные ограничения MAX — общий предел 30 запросов/с и до двух сообщений/с в диалог — передаются обязательному атомарному rate limiter репозитория; локальный процесс в одиночку их не гарантирует. [Сценарии API](https://dev.max.ru/docs/chatbots/bots-coding/prepare), [отправка](https://dev.max.ru/docs-api/methods/POST/messages).

Удалённый API не предоставляет этому адаптеру end-to-end exactly-once гарантии. Тайм-аут или успешная удалённая отправка с ошибкой локальной записи дают `unknown`; слепого повторного сообщения нет. Отмена до отправки перепроверяется; уже принятый сетью запрос нельзя гарантированно отозвать. При ошибках сохраняется только собственный безопасный код, сырые provider-ответы с токенами не журналируются.

## Ограничения текущего результата

Это подготовка инфраструктуры подключения, а не работающий бот. Настоящие сообщения, модерация, TLS-цепочка MAX, реальная БД/очередь, устойчивая конкуренция, завершённое подключение аккаунта и QR требуют отдельного стендового запуска после появления доступа. Адаптер не создаёт постоянный резервный сервер и не делает демосайт пригодным для реальных денежных торгов.
