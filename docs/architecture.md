## Общая схема

```text
Браузер / PWA                         Android / iOS (Capacitor)
        │                                      │
        └──────── общий интерфейс dist/ ────────┘
                    │
                    ├─ генератор демокаталога и клиентский поиск
                    ├─ localStorage: профиль, лоты, ставки, предпочтения
                    ├─ IndexedDB: выбранные пользователем фото и видео
                    └─ HTTPS API опубликованного сайта
                           └─ Sites → Worker → D1 DB
                                      ├─ счётчик пользователей
                                      └─ история демосделок
```

D1 не является общей базой текущих клиентских лотов и ставок. Локальная публикация объявления не делает его видимым другим посетителям.

## Порядок исполнения и основные контракты

У проекта пока нет сборщика клиентских модулей с явным графом импортов. Порядок `<script>` в `index.html` имеет значение:

1. До главного inline-скрипта загружаются правила категорий и аукциона, медиа, география, генератор демоданных, разбор поиска, рекомендации и responsive-media.
2. Главный скрипт создаёт состояние и центральные функции.
3. После него загружаются кабинет, карта, голос, платежи, уведомления, фото и модули навигации. Некоторым модулям передаются функции конфигурации.

В v66 зависимости проверяются явно:

- `listing-quotas.js` загружается до `auction-renewal.js` и форм публикации; чистый `FasListingQuotas` не активирует платный тариф. UI/автоповтор должны вызывать общую политику до записи.
- `seller-storefront.js` предшествует `seller-following.js`: каталог использует только разрешённые публичные проекции и канонические ID организаций.
- `user-agreement.js` r2 доступен до сохранения/публикации профиля. `seller-ui.js` предшествует `messages.js` и `seller-branding.js`; эти модули открывают отдельные слои, не сохраняя нижнюю форму.
- В текущем HTML `messages.js` и `seller-branding.js` следуют за `seller-ui.js`, а `buyer-tools.js` подключается позднее. Обёртки `openCar` должны сохранять предыдущий обработчик, не уничтожая действия соседних модулей. Загрузка файлов сама по себе не читает все локальные обложки или не запускает рассылку.

Не переставляйте скрипты механически и не переводите их все в `async`: это меняет доступность зависимостей. Проверяйте существование необязательных модулей и состояние открытого окна при асинхронном ответе.

## Категории, поиск, лента

`category-tree.js` задаёт пять пользовательских групп и листья. `category` сохраняет исторический базовый тип, `subcategory` — точную категорию. Для принадлежности к группе используйте API дерева, а не сравнение отображаемых русских названий. Профили характеристик в `seller-rules.js` задают уместные поля для каждой категории.

`search-intent.js` разбирает естественные условия, `keyword-search.js` сопоставляет слова и характеристики. Текстовый и голосовой поиск должны использовать общий разбор. География и расстояния рассчитываются через модули геоданных/локации; при известном только регионе расстояние приблизительное.

`featured-lots.js`, `featured-settings.js`, `recommendations.js` отвечают за верхнюю ленту. Категории в выборе объединяются, выбранные критерии пересекаются. Рекомендации берутся из локальных просмотров/избранного. Сортировка и текущая сессия просмотра не должны произвольно переставляться при лайке или обновлении цены.

## HTTP API и границы доверия

Текущие маршруты: `GET/POST /api/metrics/visit`, `GET/POST /api/analytics/sales`. Неизвестные API возвращают 404, неподдерживаемые методы — 405. API требует пользователя, доверенно установленного шлюзом Sites, и проверяет `Origin`/`Sec-Fetch-Site` до приватной работы с БД.

`oai-authenticated-user-id` доверяется **только внутри действующего контура Sites**, который устанавливает личность. Прямое развёртывание Worker на другом публичном адресе с доверием любому входящему заголовку позволяет подменять пользователя. Перед переносом нужен собственный проверяющий сессию gateway и удаление клиентских заголовков идентичности.

Sites-доступ к опубликованной странице и локальный профиль продавца — разные механизмы. Локальная проверка `sellerOwnerId` не защищает реальные общие данные. API статистики не является API ставок, переводов или регистрации.

Продажи API всегда помечены `source: demo`. Пакет — до 50 записей, тело — до 64 КиБ, история — до 10 000 записей на пользователя за 12 календарных месяцев. Сервер проверяет значения и использует параметризованные SQL-запросы. Не превращайте присланную браузером демосделку в подтверждение оплаты.

В v61 опубликован постоянный ограничитель `api_rate_limits`: фиксированные окна 60 секунд; общий бюджет `GET+POST /api/metrics/visit` — 120 запросов, чтение продаж — 60, запись продаж — 20. Каждому доверенному пользователю соответствуют максимум три переиспользуемые строки — по одной на тип API, без накопления строки на каждое окно. Допуск атомарно определяется условным SQLite UPSERT, а не памятью Worker. Превышение даёт 429 с `Retry-After`, ошибка БД/неподтверждённый допуск — 503. Проверки личности/origin и некорректного тела выполняются до обращения к счётчику. Отдельные SQLite-проверки прошли; статус общего прогона и публикации смотрите в руководстве передачи.

Это ограничение злоупотребления ресурсами приложения, не подтверждённая защита от сетевой DDoS. Каждая валидная попытка требует одной операции допуска в БД; множество разных учётных записей и двойной всплеск на границе фиксированного окна требуют отдельной оценки. Лимит не считается по IP и не заменяет защиту провайдера.

HTML/API возвращаются без общего кеширования; статика текущего закрытого сайта остаётся `private`. CSP inline-скриптов рассчитывается сборкой. Изменение аудитории, публичный CDN-кеш и перенос заголовков требуют отдельного пересмотра доступа.

## Фото, жесты и асинхронные действия

`responsive-media.js` и WebP-превью генерируются `scripts/generate-responsive-media.mjs`. Для карточек используются меньшие размеры, оригиналы остаются для подробного просмотра. Проверка SHA исходных JPEG защищает от незаметной замены изображений. Не создавайте отдельную сетевую загрузку для каждого логического crop-кадра.

Опубликованный в v65 вариант верхней галереи в `featured-lots.js`/`.css` использует вложенный нативный `.featured-photo-track`: overflow-x, scroll-snap и пассивное наблюдение жеста. Снимок движется браузером вместе с пальцем; нет overlay-стрелок, программного порога 35 px и шага на touchend. Внешняя лента прокручивает карточки вне многокадрового фото; одно фото сохраняет внешний нативный жест. Точки создаются по числу всех снимков, активность следует фактическому индексу; переход 160 ms отключается при prefers-reduced-motion.

Первый выбранный кадр присутствует статически; остальные слайды сначала не содержат IMG/src. Взаимодействие подготавливает соседей, scroll/RAF дозагружает floor/ceil видимой позиции. Загруженные кадры могут остаться в слайдах. Сохранённый URL восстанавливается в новом DOM по текущей ширине, включая скрытый контейнер с clientWidth=0 через ResizeObserver; Safari bounce ограничивается диапазоном индексов. Только изменение цены обновляет текст, оставляя тот же rail, дробный сдвиг и инерцию. Новая ссылка массива при одинаковых моделях обновляет привязку, не выключая сохранённый rail. Текущий объект проверяется по сохранённому индексу перед применением, без поиска всего каталога на каждом кадре; профиль, материалы, статус и устаревший DOM могут отменить работу. Проверки — `featured-photo-carousel.cjs` и локальный реальный DOM-fixture `featured-lots.cjs`; физический Safari не проверен.

Жестами совместно управляют `dialog-lifecycle.js`, `lot-close-gesture.js`, `back-swipe.js`, `seller-back-gesture.js`, `feed-close-gesture.js` и фото-просмотрщик. Обрабатывается только верхний слой. Шапка/ручка дают возврат; горизонтальная галерея, масштаб фото, карта, поля, выделение текста и нативная прокрутка сохраняют приоритет. Нельзя добавить глобальный `preventDefault` для любого касания.

После `await` проверяйте поколение действия, открытое окно и текущий лот/профиль. Поздний Clipboard, геолокация, фото или распознавание речи не должны открыть окно поверх уже другого процесса. Тесты возврата проверяют позицию, критерии и введённую ставку, а не только факт закрытия.

`createFasDialogBlankBack` в `back-swipe.js` различает завершённый физический тап по свободной области и нативные действия. Перед озвучкой/после parser callback заново проверяются текущий профиль, поколение, свежие предпочтения и актуальность предложения. Мемоизация сводки хранит исходные байты workspace и владельца до следующего изменения; голосовые запросы без местоположения пропускают проход городов. `search-intent.js` отделяет единицы и числовые идентификаторы от денег; неподдерживаемые отрицания/валюты/альтернативы/относительный возраст получают явное уточнение. [18 positive + 22 clarification](search-followup-audit-2026-11-14.md) проходят через настоящий ввод и голос.

Детальные причины и целевые проверки: [возврат/фото](interaction-followup-audit-2026-11-14.md), [контекст/безопасность](security-followup-audit-2026-11-14.md), [производительность](performance-followup-audit-2026-11-14.md). Замороженные результаты 194/194 относятся к v61, а не ко всем этим изменениям.

## Шифрование и границы общения

Сквозное шифрование сайта или чата не внедряется. Подготовленный интерфейс сообщений хранит черновики по локальному владельцу и не обеспечивает обмен между людьми. Настоящая доставка/модерация требуют подтверждённых серверных аккаунтов, проверки участников, прав по роли и аудита; статусы отправки/прочтения и счётчики непрочитанных не подменяются локальными данными. HTTPS, защита данных/резервов и отдельные ключи — требования серверного запуска, не заявление о проверенном шифровании всех хранилищ. Обычные сообщения Telegram-бота не имеют end-to-end защиты: только краткий статус и защищённая ссылка, без документов и платёжных данных.

## Куда развивать архитектуру

### Коммерческий этап и модель хранения имущества

[Требования первого запуска](launch-requirements.md): по сведениям владельца — 100 партнёрских организаций (50 банков и 50 коллекторских), 13 площадок собственной сети хранения по России и около 1300 автомобилей. Это входные бизнес-сведения, не верифицированные партнёрства/остатки и не подключённый источник каталога. Адреса и данные фактического учёта не получены; публичный демокаталог/счётчики ими не заполняются.

Первая коммерческая область — имущество банков, частных продавцов и партнёрских организаций. Государственные торги отложены и выключены; факт хранения государственного предмета не даёт права запустить такую процедуру через обычный лот.

Будущая модель раздельно хранит `owner` (собственник), `seller` (продавец), `authorizedPublisher` (публикатор по мандату), `custodian` (хранитель), `yard` (фактическая площадка) и внешнее место хранения. Это названия смысловых сущностей, не заявление о готовых таблицах/API. Операторская площадка не подменяет собственника/продавца; адрес стороннего банковского имущества не выводится из адреса банка или ближайшей собственной площадки.

Для всех типов продавца хранение в сети оператора добровольное. Публикация допускает законное фактическое место вне сети без договора хранения с оператором; обязательность такого договора нельзя включать в общий валидатор объявления. Отдельные договор/мандат проверяются только при выборе услуги конкретной площадки сети. Подготовленный [контракт интеграций](../integrations/contracts/contracts.cjs) является программной границей, а не действующей внешней интеграцией.

Пакет `integrations/contracts/` содержит реализацию валидаторов, TypeScript-типы, JSON-схемы и [описание](../integrations/contracts/README.md); `tests/integration-contracts.cjs` прошёл. `validateListingIdentity` связывает `subjectId`/`subjectFingerprint`, источник `bank|private|partner`, ID участников и организации, вариант хранения и доверенные полномочия. Государственный источник закрыт; публикация от чужого имени требует проверяемого мандата. Привязка назначенных площадок регулирует действия хранителя, а не принуждает все внешние лоты к сети. `assertListingIdentityUnchanged` сравнивает каноническую идентичность после ставки/результата. Подлинность `trustedGrant`, серверная сессия, реальный журнал/банковские подписи и атомарность должны обеспечиваться отдельной реализацией, которой пока нет.

Для серверного портала нужны организационная изоляция данных, собственные/назначенные лоты, мандаты с областью и сроком, отдельные права управляющего площадкой на фото/документы/осмотр, аудит действий и безопасный отзыв полномочий. Импорт должен сохранять организацию/стабильный внешний ID, проверять фактическое хранение и не менять предмет/условия после ставки. Типизированный контракт и демоформа сами по себе не обеспечивают эти права и не означают подключённый портал.

### Постепенное развитие

Главный inline-скрипт пока велик, а модули используют общие глобальные функции. Это технический долг. Выделять состояния/сервисы следует постепенно с сохранением контрактных проверок, без полной переписи одновременно с изменением поведения торгов.

Общие реальные торги потребуют серверных пользователей/ролей, транзакционного журнала ставок, доверенного времени, единственного результата продажи, платёжных событий и файлового хранилища. Этапы и критерии испытаний — в [capacity-plan.md](capacity-plan.md), дополнительные архитектурные расчёты — в [SCALING.md](SCALING.md). Их нельзя выдавать за уже работающий сервер. Миллион зарегистрированных аккаунтов и 100–900 тысяч активных не определяют одновременную нагрузку без периода активности и измерений.

Отдельная [проверка объёма 10/100 тыс. записей](capacity-audit-2026-11-14.md) прошла на неизменённом Worker/SQLite: 280 вызовов, четыре соединения и максимум четыре параллельных запроса, ожидаемые счётчики/изоляция/квоты сохранены. Индексный онлайн-подсчёт и агрегаты полной истории остаются местами роста SQL-работы; это основание для следующего серверного этапа, не доказательство 100 тыс. одновременных клиентов или пропускной способности D1.
