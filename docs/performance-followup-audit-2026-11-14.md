# Дополнительный аудит производительности

14 ноября 2026 года. Базовые версии первых двух модулей взяты из опубликованного коммита `bfcf16772ecffc2735b54d05c2c9f2e6fb08fcfb` (v61). Проверка исполняет реальные клиентские модули в изолированной Node VM; опубликованный сайт запросами не нагружался.

## Найдено и исправлено

| Операция | До | После |
|---|---:|---:|
| Дополнительные разборы неизменного workspace 400 079 байт при 100 обновлениях сводки | 100 | 0 |
| Проходы по каталогу сводки в том же опыте | 1 | 1 |
| Чтения поля города для пяти голосовых запросов без местоположения, каталог 52 870 лотов | 1 057 410 | 0 |
| Обращения `prepare()` к строкам холодного каталога для каждого ошибочного запроса | 52 870 | 0 |
| Задачи индексации, запланированные `prepare()` для каждого такого запроса | 1 | 0 |

Сводка проверяла кеш результатов уже после разбора полного профиля. Теперь один снимок исходной строки и допустимый ID владельца переиспользуются, пока байты не изменились. Новый регрессионный тест вызывает стандартный production-путь профиля, а не адаптер `getProfileId`, и дополнительно проверяет повторные события прокрутки в варианте без IntersectionObserver. Изменение профиля, повреждённые данные, неподдерживаемая схема, удаление профиля, отказ и восстановление хранилища проверены отдельно. Отказ чтения не подставляет прежнего владельца.

Голосовой обработчик строил список городов всех лотов даже для фразы «Найди красный седан». После общего обработчика местоположения теперь проверяется наличие той же конструкции с предлогом, которую принимает запасной поиск по каталогу. Если такой конструкции нет, полный проход не запускается. Стандартные города по-прежнему распознаются общим модулем, а неизвестные ему населённые пункты — по актуальному каталогу. Проверены `в`, `из`, `около`, `рядом с`, `in`, `near`, `around`, `from`, регистр, перенос строки и замена каталога. Кеш городов не добавлялся, поэтому дополнительная логика его сброса не нужна.

Тот же голосовой файл получил согласованную предпроверку канонической ошибки запроса до извлечения чисел: сведения о неподдерживаемой валюте или отрицательном условии сохраняются, а известная модель имеет приоритет. Это изменение проверяется отдельно сценариями поиска. Неоднозначные значения километров сохраняют прежний режим радиуса; для пробега используется явное уточнение.

Отдельно координатор выявил лишнюю подготовку при уже известной ошибке запроса. `FasKeywordSearch.prepare()` строил список ожидающих индексации лотов даже после того, как канонический разбор потребовал уточнить валюту или неверный диапазон. Теперь функция возвращает прежний результат пустой подготовки до создания индекса идентификаторов, `filter()` и планирования задач. Три запроса — неподдерживаемая валюта, обратный диапазон цены и обратный диапазон площади — проверены на холодных 52 870 записях: ноль обращений к строкам, ноль чтений индексируемых полей, ноль задач. В исходной функции каждый такой запрос читал 52 870 строк и планировал задачу; исполнение одной первой порции читало 200 полей. Это измерение именно `prepare()`, а не нулевой работы всей страницы.

Для третьего случая исходная реализация `prepare()` до исправления проверялась с текущим каноническим разбором, который уже возвращает новые ошибки уточнения. Это не утверждение, что опубликованный v61-парсер сам выдавал все эти ошибки. Валидная подготовка 251 записи всё ещё проходит тремя порциями с прогрессом, результат поиска доступен; отмена останавливает большой каталог после первой сотни записей.

При раздельной подстановке исходного v61-модуля он воспроизводимо падает на соответствующей проверке, что подтверждает причинную связь. Вместе с новым регрессионным файлом прошли 12 связанных файлов: сводка, голосовые команды, персонализация, действия со ставкой, автозапуск безопасных команд, локальный ИИ, сложные поисковые запросы, подготовка/жизненный цикл индекса, объём работы поиска и границы идентификаторов.
