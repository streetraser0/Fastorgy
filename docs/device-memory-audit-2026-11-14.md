# Память на iPhone и Android: проверка доступности и протокол замера

Проверено 14 ноября 2026 года, 21:31–21:33 UTC. **Фактическое потребление RAM сайтом на iPhone и Android пока не измерено: подключённых телефонов нет.** Этот документ фиксирует выполненную проверку среды и подготовленный порядок аппаратного измерения. DOM-модели, heap Node.js, размер файлов и память Linux не выдаются за память телефона.

## Почему размер файлов — другое измерение

В 21:32:41 UTC сумма размеров 261 публичного файла `dist/`, без сгенерированных `server/`, `.openai/` и `drizzle/`, составила **12 121 306 байт: 12,12 МБ или 11,56 МиБ**. Это объясняет ранее обсуждавшиеся «около 12,1 МБ»: посчитаны несжатые файлы на диске, а не RAM и не объём первой загрузки. Браузер загружает выбранные ресурсы с учётом кеша и приоритетов, а изображения в памяти декодируются.

Для иллюстрации, один буфер RGBA 1200 × 800 × 4 занимает 3 840 000 байт независимо от размера JPEG/WebP на диске. Это расчёт формата буфера, **не измерение памяти конкретного телефона**. Реальная страница дополнительно использует DOM, JavaScript, стили, изображения, слои, видеобуферы, движок и вспомогательные процессы.

В тот же момент `du -sb` для всей рабочей папки проекта показал **2 622 680 424 байта**. Обсуждавшиеся «около 2,7 ГБ» относятся к рабочим материалам вместе с SDK, зависимостями, сборками, архивами и исходниками. Эта папка целиком не передаётся посетителю. Объём каталога разработчика, сетевой трафик и RAM нужно отражать разными строками отчёта.

## Общий сценарий для двух телефонов

Измерять один и тот же опубликованный commit/номер выпуска; отдельно браузер, установленную PWA и приложение. Записать модель и общий объём RAM устройства, версию ОС/браузера/WebView, сборку, состояние кеша и подключённость профилировщика. Серийный номер не нужен. Пользовательские данные заменить собственным тестовым профилем.

1. Открыть одну контрольную пустую вкладку; зафиксировать фон и набор процессов. Затем открыть сайт, дождаться завершения начальной загрузки и 30 секунд без действий. Холодный и тёплый запуск записывать отдельно.
2. Пролистать верхнюю ленту и фотографии минимум у 10 лотов; выполнить медленное перетягивание, быстрое движение и возврат к первому кадру. Проверить обновление цены во время движения и отсутствие случайного открытия лота.
3. Выполнить 20 циклов «открыть лот → фотографии/масштаб → закрыть → открыть кабинет → закрыть». Сохранять одинаковое число действий на обоих устройствах. Отдельно открыть карту, сменить поиск и вернуться в ленту.
4. В контрольных точках записать исходный уровень, пик и уровень после 30–60 секунд покоя. Сравнить три одинаковых прогона, а не один момент. Не запускать принудительный GC перед каждым обычным измерением; диагностический прогон с GC помечать отдельно.
5. Локальный ИИ проверять отдельным явным сценарием: до включения, после загрузки/инициализации, после запроса и после выключения. Размер файла модели не равен его RAM. Обычная загрузка сайта не должна включать модель сама.
6. Сохранить временные метки, задержки/перезагрузки вкладки, предупреждения о памяти и трассы. Повторяемое увеличение остаточного уровня после одинаковых циклов требует расследования; только рост пика не доказывает утечку.

## iPhone: Safari Web Inspector и отдельный системный footprint

Нужны физический iPhone, доверенное подключение к Mac и совместимые версии Safari/Xcode. На iPhone включить **Настройки → Приложения → Safari → Дополнительно → Web Inspector**; на старых iOS раздел Safari находится прямо в Настройках. На Mac включить инструменты разработчика в Safari. В меню **Develop / Разработка → Inspect Apps and Devices / имя устройства** выбрать именно вкладку сайта на iPhone; не локальную вкладку Mac и не Simulator. Порядок подключения описан в [официальной справке Apple](https://developer.apple.com/documentation/safari-developer-tools/inspecting-ios) и [WebKit](https://webkit.org/web-inspector/enabling-web-inspector/).

В Web Inspector открыть **Timelines**, включить **Memory** и записать общий сценарий выше. Сохранить разбивку JavaScript / Images / Layers / остальной памяти страницы. Для поиска удерживаемых DOM-узлов и объектов использовать JavaScript Allocations/heap snapshots до и после циклов. Это сведения инспектируемого веб-контента; их нельзя автоматически назвать полным системным RAM браузера. Различие инструментов объясняет [WebKit: Memory Debugging](https://webkit.org/blog/6425/memory-debugging-with-web-inspector/).

Для системной памяти приложения открыть свой диагностический проект в Xcode, выбрать **физический iPhone** и выполнить **Product → Profile**. В Instruments выбрать **Allocations**, добавить/включить **VM Tracker**, а для отслеживания footprint — доступный memory report. Записать пики и остаток для тех же действий. Показания heap и footprint сохранять отдельно: footprint включает не только heap. Методика Apple — [Analyze heap memory](https://developer.apple.com/videos/play/wwdc2024/10173/).

У приложения с WKWebView есть отдельный WebContent и другие процессы. Цифра хост-приложения сама по себе не равна сумме памяти веб-страницы. По возможности отдельно измерить разрешённые системой связанные WebContent/GPU-процессы, указав состав и название метрики; общие процессы не складывать вслепую. Для обычного Safari доступ Instruments к системным процессам может ограничиваться ОС и правами: если нужный footprint недоступен, отметить **«системный footprint Safari/WebContent не получен»**, сохранив доступный Web Inspector trace. Не подменять его памятью Mac, Simulator или всего устройства.

Инспекция WKWebView требует доступного для разработчика inspectable-контента. Это условие диагностической сборки, а не повод включать отладку всем пользователям. Приложение и Safari/PWA — отдельные результаты, даже при одинаковых веб-файлах.

## Android: Chrome и Android Studio / ADB

На собственном тестовом телефоне включить USB debugging, подтвердить доверие компьютеру. Проверить, что ADB показывает ровно выбранное разрешённое устройство. В настольном Chrome открыть **`chrome://inspect/#devices`**, выбрать вкладку сайта на физическом Android. Для приложения выбирать его WebView, а не вкладку настольного Chrome. Порядок — [Chrome: Remote debug Android devices](https://developer.chrome.com/docs/devtools/remote-debugging).

В DevTools записать Memory/Performance с общим сценарием: JS heap, DOM и удерживаемые объекты помогают найти причину роста, но не дают полного PSS/RSS. Для `ru.fastorgi.app` открыть Android Studio Profiler на этом же устройстве; сохранённый heap dump хост-приложения не включает весь heap отдельного Chromium renderer. Применять [официальный протокол WebView memory](https://developer.android.com/topic/performance/memory/guide/webview-memory).

Точечные команды на подключённом собственном телефоне; `<PID_...>` заменить локально найденным процессом, не выполнять буквально:

```sh
adb shell pidof ru.fastorgi.app
adb shell dumpsys meminfo ru.fastorgi.app
adb shell ps -A -o PID,PPID,NAME
adb shell dumpsys meminfo <PID_РЕНДЕРЕРА_ЭТОГО_ПРИЛОЖЕНИЯ>
adb shell dumpsys meminfo <PID_СВЯЗАННОГО_GPU_ПРОЦЕССА>
```

Связь renderer с целевой вкладкой/приложением подтвердить по процессам и service bindings Android Studio/системной трассы; не считать любой `sandboxed_process` процессом нашего сайта. Команды выполнять отдельно в контрольных точках. **TOTAL PSS**, **TOTAL RSS**, Native/Java/Graphics/Private Other и SwapPss, если доступны, сохранять с единицами и временем. Если RSS или GPU недоступны на данной ОС, записать это прямо. [Android `dumpsys`](https://developer.android.com/tools/dumpsys) объясняет значения и различия PSS/RSS.

PSS распределяет общие страницы между процессами; сумма PSS выбранной связанной группы полезна для оценки её веса. Простая сумма RSS может повторно посчитать общие страницы. WebView renderer учитывается отдельно от `ru.fastorgi.app`; Java heap хоста не показывает весь V8/DOM. Для Chrome с несколькими вкладками нельзя приписывать весь `com.android.chrome` одному сайту. Использовать контролируемую одну вкладку, базовый замер и явно помеченную разницу группы процессов; это всё равно не абсолютно изолированная RAM одной страницы.

После профилирования закрыть инспектор и отключить диагностическое подключение. Debug/profile-сборка и инспектор сами вносят накладные расходы; для сравнения использовать одинаковый режим и отдельно проверить обычный запуск без инспектора.

## Что не является достаточным замером

- `performance.memory` — устаревшее нестандартное расширение Chromium для JS heap. Оно не является переносимым API Safari и не покрывает изображения, GPU, нативные буферы и все отдельные heaps/процессы. Его наличие проверяется как возможность; отсутствие не ошибка сайта. [Описание API](https://developer.mozilla.org/en-US/docs/Web/API/Performance/memory).
- `performance.measureUserAgentSpecificMemory()`, где поддерживается, также имеет ограничения поддержки и условий безопасности; его нельзя выдавать за универсальный системный PSS/RSS телефона.
- `navigator.deviceMemory` сообщает приблизительный класс общего объёма памяти устройства, а не потребление сайта.
- Сборка APK, совпадение файлов, Node/DOM-тесты и `process.memoryUsage()` не измеряют RAM Safari/Chrome на физических телефонах.
- Network transferred/resource size, Cache Storage/IndexedDB, размер модели и публичных файлов — не RAM. Объём всего браузера или всей системы — не доказанная память одной вкладки. [Chrome различает OS footprint и JS heap](https://developer.chrome.com/docs/devtools/memory-problems).

## Форма будущего результата

| Поле | Что записать после аппаратного прогона |
| --- | --- |
| Версия | Номер опубликованного выпуска и полный commit |
| Устройство | Модель, общий объём RAM, ОС, Safari/Chrome/WebView; без серийного номера |

| Нагрузка | Количество лотов, фото и повторений общего сценария, длительность |
| Повторяемость | Не менее трёх одинаковых прогонов, диапазон результатов, рост остатка |
| Подтверждения | Обезличенная трасса/heap snapshot, время, перезапуски/сбои и ограничения доступа к процессам |
