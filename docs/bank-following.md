# Банки, партнёры и подписки на продавца

Этот модуль подготовлен отдельно от опубликованного сайта. Само наличие исходников не означает подключение защищённых кабинетов банков, серверной публикации, доставки уведомлений или Telegram/MAX. Публикацию и интеграцию выполняет основной разработчик после общего прогона.

## Что получает пользователь

Кнопка «Банки и партнёры» открывает каталог организаций из доступных публичных объявлений. В нём можно искать название или город, выбирать банки, лизинговые компании либо организации/партнёров, открывать лоты продавца и фильтровать сохранённые подписки.

В публичном профиле организации есть «Подписаться на новые лоты» / «Вы подписаны». Второе нажатие отменяет подписку. Настройка сохраняется только для текущего локального профиля и только на этом устройстве. Это **не подключает рассылку**: внешняя доставка и защищённые серверные аккаунты ещё отсутствуют.

Данные каталога берутся из публичных лотов. Неопубликованные черновики, будущие объявления, приостановленные и удалённые записи не становятся карточками организаций. Завершённая история показывается только при наличии публичных признаков размещения. Количество лотов — фактическое число доступных публичных записей, а не подтверждённые реальные сделки. Демопродавцы отмечены как демопрофили. Отметки «проверен», отзывы, число подписчиков и список якобы реальных банков не генерируются.

Для подписки нужен общий канонический идентификатор организации. Совпадающие названия не объединяют разные организации. Если ID отсутствует или противоречит другим указанным ID, публичный профиль остаётся отдельным объявлением; подписка на него как на организацию недоступна. Физические лица в каталоге банков и партнёров не перечисляются.

## Файлы и включение

- `dist/seller-storefront.js`: публичные проекции организаций и сохранение существующего маршрута профиль → лот → профиль.
- `dist/seller-following.js`: каталог, локальные предпочтения и явные действия подписки. Подключается **после** `seller-storefront.js`; модуль не читает весь каталог и хранилище при загрузке.
- `dist/seller-storefront.css`: существующие профили и оформление нового каталога/подписки.
- `tests/seller-following.cjs`: самостоятельные проверки.

Основной код должен добавить отслеживаемый ресурс, обновить версию ссылки/кеша, мобильные копии и затем собрать Worker. Пример подключения (метку версии выбирает выпускающий разработчик):

```html
<script src="seller-storefront.js?v=RELEASE"></script>
<script src="seller-following.js?v=RELEASE"></script>
```

В выбранном месте публичной навигации используется обычная кнопка:

```html
<button type="button" class="outline" data-open-seller-directory>
  Банки и партнёры
</button>
```

Она не предоставляет права сотрудника банка и не заменяет закрытую панель управления. После отрисовки публичного профиля вызывается необязательный `FasSellerBranding.decorate(storefrontBody, identity(anchor))`. Его асинхронная проверка владельца принадлежит модулю оформления; каноническая личность продавца остаётся видимой. Оформление организаций не разрешается одним заявленным типом продавца.

Модуль не добавляет элемент в глобальное меню самостоятельно, чтобы основной разработчик сохранил согласованную мобильную компоновку.

## Интерфейсы

`FasSellerStorefront.publicOrganizations({force:true})` возвращает только публичные сводки; `publicSellerInfo(lotId,{force:true})` повторно разрешает организацию конкретного публичного лота. Публичные DTO содержат имя, заявленный тип, город/агрегат городов, признак демо, количества активных/завершённых записей и ID опорного объявления. Внутренний `key` предназначен для сопоставления подписки; он не выводится в разметку. Данные частного кабинета продавца, отзывы, банковские реквизиты и кошелёк не читаются.

`FasSellerFollowing` предоставляет:

| Метод | Назначение |
| --- | --- |
| `openDirectory(trigger)` / `closeDirectory()` | Открытие и возврат только из верхнего окна |
| `refreshDirectory()` | Явное обновление публичного каталога |
| `directoryState()` | Текущие поиск/тип/страница и публичные ID показанных организаций |
| `followingState()` | Доступность локального хранения, число подписок и канонические ключи текущего зрителя |
| `configure({getViewerId,storage})` | Необязательные адаптеры. По умолчанию берётся только `FasSellerUI.getProfile().id` и `window.localStorage` |
| `mountProfile(dialog,lotId)` | Внутренний слот подписки в уже открытом публичном профиле |
| `suspendDirectoryForLot()` / `resumeDirectoryForLot(token)` | Внутреннее сохранение нативного порядка окон при переходе к лоту |

`getViewerId` — идентификатор локального пространства предпочтений, **не серверная авторизация**. Сводки каталога кэшируются по ссылке/длине источника и его ревизии, до ближайшей временной границы публичности либо максимум 30 секунд. Обновление выполняется только при явном открытии/кнопке обновления; таймеров и MutationObserver-сканирований нет. Повторное открытие свежего кэша не проходит весь инвентарь. Перед подпиской доступность конкретного канонического продавца перепроверяется.

Модуль извлекает только ID текущего зрителя; личные поля этого профиля не попадают в публичный профиль организации, разметку или записи подписки.

## Хранение и ошибки

Ключ локального хранилища: `fas-seller-following-v1:` + URL-кодированный ID зрителя. Формат:

```json
{
  "version": 1,
  "owner": "local-profile-id",
  "revision": 1,
  "entries": [
    {
      "sellerKey": "organization:canonical-public-organization-id",
      "subscribedAt": "2026-11-14T00:00:00.000Z"
    }
  ]
}
```

В записи нет телефона, email, названия продавца, названия лота или сообщения. Размер ограничен 128 КиБ, число записей — 200: это технический лимит локального демо, а не согласованный коммерческий тариф. Серверный лимит должен определяться отдельно.

Перед записью повторно проверяются текущий зритель, верхнее окно, принадлежность кнопки актуальному DOM, канонический продавец и публичность опорного объявления. Затем сравнивается исходный снимок хранилища, увеличивается ревизия и проверяется записанный результат. Это защита от **обнаруженного** конфликта, не межвкладочная атомарная транзакция. Не выдавать её за финансовую или серверную гарантию.

Сбой памяти, чужой `owner`, неверная схема, неизвестная версия, переполнение или обнаруженный конфликт дают явную ошибку. Подписка не отмечается успешной до подтверждённой записи; испорченные данные не затираются пустым списком. После конфликта следует заново открыть профиль/обновить каталог и повторить действие.

Переход каталог → профиль → лот → профиль → каталог сохраняет поиск, тип, страницу, прокрутку, исходное окно и введённую ставку. Для сохранённой подписки без текущих публичных лотов в «Моих подписках» остаётся отдельная карточка «Продавец временно недоступен» с кнопкой удаления. Новая подписка по непубличному ID не создаётся. Название удалённого продавца не восстанавливается из частных данных.

Каталог временно закрывается перед открытием уже существующего основного диалога лота, чтобы не остаться выше него в нативном top layer. Возврат восстанавливает порядок окон; отложенный close не восстанавливает старый маршрут после повторного открытия. Токен возврата привязан к текущему зрителю и сеансу каталога.

## Серверный контракт для реального запуска

Следующие маршруты и таблицы — **требования будущего подключения**, их обработчики этим модулем не создаются.

1. Сервер получает пользователя из подтверждённой сессии. Поля `owner` из браузера, название банка и переключатель демороли не дают права от имени пользователя или организации.
2. Публичный реестр продавцов разрешает настоящий `sellerOrganizationId`, его статус публикации и законность доступных публичных полей. Демо-ключи `demo-organization:*` не переносятся в настоящий реестр.
3. Таблица `seller_follows` имеет уникальность `(principal_id, seller_organization_id)`, статус, ревизию, время создания/отмены и версию согласия. Добавление/удаление — транзакционно, с идемпотентным ключом запроса и проверкой ожидаемой ревизии.
4. Пример интерфейсов: `GET /api/public/sellers`, `GET /api/me/seller-follows`, `POST /api/me/seller-follows`, `DELETE /api/me/seller-follows/:id`. Публичные выдачи используют пагинацию; пользовательские маршруты всегда выводят `principal_id` из сессии и проверяют принадлежность записи.
5. Только каноническое серверное событие `lot.published` связывается с организацией и активными подписками. Изменяемый локальный каталог и браузерное событие не запускают реальную рассылку.
6. Канал доставки включается отдельным согласием и проверенной привязкой Telegram/MAX. Привязка мессенджера не получается из чужого ID или скопированной ссылки. Категории, бюджет, регион, частота и тихие часы применяются вместе с подпиской на продавца.
7. Очередь связывает событие, пользователя, ревизию подписки и поколение привязки канала. Перед отправкой повторно проверяются действующая подписка, разрешённый получатель, настройки и публичность лота. Отмена подписки или перепривязка канала блокирует старые отложенные сообщения.
8. Ошибки неизвестного результата отправки не означают безопасный автоматический повтор. Требуются устойчивый inbox/outbox, политика повторов и журнал без секретов/лишних персональных данных.

Локальные настройки нельзя молча считать серверным согласием на рассылку. При миграции нужен явный подтверждённый импорт и проверка каждого канонического ID. Серверные кабинеты банков с правами сотрудников, изоляция организаций, финансовые операции, чат и модерация — отдельные подсистемы.

## Проверки

```sh
node tests/seller-following.cjs
node tests/seller-storefront.cjs
node tests/seller-storefront-return-routes.cjs
```

Новый тест проверяет каноническую группировку, фильтры, публичность, отсутствие холодного прохода по 52 тысячам записей, профильные пространства подписок, обнаруженный конфликт/квоту/ошибки памяти, запрет подписки на неподтверждённый одиночный ID, экранирование удаление недоступной подписки, защиту фокуса от запоздалого закрытия и возврат с исходной ставкой. Это Node/DOM-модели; физический Safari и Android отдельно не тестировались. Перед публикацией основной разработчик выполняет подходящие соседние проверки, обязательный pre-push и сверяет мобильные файлы.
