# Контракты будущих подключений

Это небольшой серверный слой проверки границ интеграций. Он не подключает банк, ИИ, регистрацию, реестр общих торгов или резервный сервер. Публичные финансовые API по-прежнему закрыты. Файлы этого каталога не должны попадать в браузерный `dist/`.

## Начать работу

```sh
node tests/integration-contracts.cjs
```

- `contracts.cjs` — исполняемые проверки и оболочки для серверных обработчиков.
- `contracts.d.ts` — типы и объяснение доверенных данных.
- `schemas.json` — локальные JSON Schema для транспортных документов; удалённых схем и запросов нет.

JSON Schema проверяет структуру. Дополнительные числовые, временные и бизнес-инварианты проверяются исполняемым кодом. Схема не является реализацией маршрута, авторизации или миграцией БД.

## Банк и обеспечение ставки

Провайдером будущего подключения выбран Т-Банк. Конкретный продукт, возможность обеспечения аукциона до 30 суток с продлением и расчётом, договор и правила раскрытия средств ещё не подтверждены. Обычный карточный холд нельзя автоматически считать эскроу.

```js
const { createBankAdapter } = require('./integrations/contracts/contracts.cjs');
const bank = createBankAdapter();
// Любой вызов отклоняется с integration-disabled. Запрос к банку не выполняется.
```

Включение требует серверной конфигурации `state: 'ready'`, `reviewReference`, `provider: 'tbank'`, `productReference`, `maxHoldMinutes` и двух явно переданных обработчиков:

1. `authorize(context, operation, command)` получает доверенный контекст подтверждённой серверной сессии. Он повторно читает актуальный лот, версию, права, владельца, ограничения и состояние обязательств из БД. Пользователь не передаёт `principalId`, права или признаки готовности в команде.
2. `execute(job)` — будущий серверный координатор. Он проверяет постоянный журнал команд, банковский статус и выполняет разрешённое действие через проверенный банковский адаптер. Это **не** прямой callback из браузера и **не** готовый HTTP-клиент Т-Банка.

`reviewReference` — ссылка оператора на проведённую проверку конфигурации, а не банковская аттестация. Наличие строки или переключение флага не доказывает готовность банка.

Денежные значения передаются как `{currency: 'RUB', kopecks: '12345'}`: целое число копеек в канонической десятичной строке. Дробные числа, экспоненты, знак, ведущие нули и выход за `9007199254740991` копеек отклоняются. Для ставки требуется положительная сумма; баланс может быть нулевым.

`createHold` проверяет полный размер ставки по подтверждённым свободным средствам **за вычетом других резервов**, чужой лот, действующий срок и банковское покрытие до срока расчёта. Доверенный `protectedEndsAt` должен включать исходный срок и применимые продления; `settlementDeadline` не может быть раньше него. Эти даты поступают из серверной политики, не от покупателя. Неподходящий продукт блокирует действие.

Обёртка не создаёт распределённую транзакцию. До включения `execute` обязательны:

- постоянный уникальный ключ `(principal, operation, idempotencyKey)` и отпечаток канонической команды;
- одинаковый ключ с другим содержимым — конфликт; повтор того же запроса — подтверждённый прежний результат;
- атомарная проверка версии лота и выделение средств в серверном реестре обязательств;
- запрет использования одних средств в нескольких обязательствах;
- outbox/согласование с банком и компенсации при частичном выполнении;
- проверка банковских уведомлений штатным способом выбранного продукта;
- при неизвестном исходе — сверка по той же операции, без слепого повтора списания.

`releaseHold` и `settle` требуют отдельного разрешения доверенного координатора. После успешной проверки результата наружу возвращаются только разрешённые поля. Скриншот, `paid=true`, return URL и клиентский `funded` не являются доказательством банковского события. `verifyEvent` — контракт вызова будущего доверенного обработчика по сохранённой ссылке на событие; проверка подписи, raw-body, защита от повторов и сопоставление события операции остаются обязанностью банковского координатора. Ни одной схемы подписи или URL банка здесь не выдумано.

## ИИ

`createAssistantAdapter()` по умолчанию отключён. После подключения `interpret` получает только ограниченную фразу и язык `ru`. Выход проверяется: внутренний переход, поиск, запрос статуса, настройка оповещений либо **подготовка** ставки. Покупка, платёж, удаление, JavaScript, произвольный URL и команда непосредственной ставки отклоняются.

Подготовленная ставка всегда имеет `requiresHumanConfirmation: true`. Итоговая отправка должна пройти штатный серверный обработчик и повторные проверки. Модель не получает полномочия совершать сделку из своего текста. Настоящая модель, бюджет запросов, согласованные цели передачи данных, rate limits, журналирование без секретов и правила поддержки подключаются отдельно.

## Владение, продавец, размещение и хранение

Первый коммерческий этап: `bank`, `private`, `partner`. Государственные торги отключены и требуют отдельной реализации правил и проверки применимости закона.

`validateListingIdentity` разделяет `ownerId`, `sellerId`, `publisherId`, `sellerTenantId`, `custodianId` и место хранения. Хранение не доказывает право собственности или продажи. Для размещения от имени продавца нужна действующая проверенная доверенность/полномочие в серверном реестре; флаг из пользовательского тела не принимается.

Место хранения — наша площадка, территория продавца или третьего лица. Наши площадки не обязательны для банков, частных лиц и партнёров. Внешнее местонахождение может задаваться закрытой ссылкой `locationRef`; полный адрес не обязательно публиковать. Для собственной площадки назначение и хранитель сверяются с доверенным реестром. Роль сотрудника площадки сама по себе не открывает доступ к чужому tenant.

`assertListingIdentityUnchanged` сравнивает предметные поля с канонической записью при принятой ставке или сохранённом результате. Фактические `acceptedBidCount`, результат и предыдущую запись берут из серверного журнала. Проверка не заменяет блокировку строки/версионную запись в БД.

`subjectId` привязывает запись к конкретному активу, а `subjectFingerprint` — к его неизменным идентифицирующим характеристикам. Отпечаток сервер вычисляет из канонических VIN/кадастрового/серийного номера и существенных свойств. Нельзя принимать присланный клиентом хеш как доказательство предмета или права собственности: он сравнивается с доверенной записью полномочий и объекта.

Плановые 100 партнёров, 13 площадок и около 1300 автомобилей не превращаются в тестовые публичные объявления. Адреса, договоры, мандаты, остатки и фиды предстоит получить и проверить.

## Регистрация и юридические версии

Схема `authRequest` содержит отдельные отметки соглашения и телефонного согласия. Клиентские дата и версия — метаданные запроса. Сервер должен сверить текущую обязательную версию/хеш неизменного текста, записать собственное время и подтверждённую личность при завершении OTP. Сам чекбокс не доказывает успешную регистрацию или подпись подтверждённого лица. Реальные OTP, сессии и серверный реестр пока отсутствуют.

## Восстановление

`validateRecoveryManifest` принимает версию исходников, SHA-256 файлов согласованного snapshot БД/медиа/исходников, **только имена** переменных окружения и требование сохранять закрытую аудиторию, доверенный шлюз и управляемый оператором DNS. Относительные пути без обхода каталогов и одинаковый `snapshotId` обязательны.

Этот манифест не создаёт копии, не проверяет содержимое по указанному хешу, не разворачивает сервер и не переключает DNS. Резервные копии, ключи в отдельном хранилище секретов, шифрование, проверка полноты данных, независимая площадка, защита от удаления и пробное восстановление подключаются отдельно. Прямое публичное развёртывание Worker с доверенным заголовком личности без соответствующего шлюза недопустимо.

Производительность для миллиона аккаунтов и числа активных пользователей этими контрактами не подтверждается. Для неё нужны настоящая серверная система, согласованная модель одновременной нагрузки и отдельные испытания.
