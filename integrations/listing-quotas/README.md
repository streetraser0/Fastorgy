# Лимиты активных объявлений: серверная граница

Это подготовленный **отключённый серверный** модуль. Он не подключён в Worker, оплату или подтверждённые аккаунты и не предоставляет платные права. Отдельная бесплатная проверка для локальной демоформы реализована в `seller-ui.js` и подключается загрузкой общего `listing-quotas.js`; её нельзя выдавать за защищённый серверный контроль. Изменение `state` на `ready` само по себе не создаёт безопасное хранилище.

- `../../dist/listing-quotas.js` — чистые правила сервера и демо-адаптация локальных лотов. Browser API — `FasListingQuotas`, CommonJS — `require(...)`. Демо-функции не подтверждают личность, организацию или оплату.
- `adapter.cjs` — отключённый по умолчанию серверный координатор. Он принимает только идентификатор уже проверенного изменения, а не произвольную категорию/тариф/владельца из браузера.
- `adapter.test.cjs` — изолированные проверки с **тестовым** сериализуемым хранилищем в памяти; не готовая production-БД.
- `config.example.json` — утверждённая бесплатная политика, незаполненные платные лимиты и неактивный пример договора организации.
- Полное описание и включение — [../../docs/listing-quota-policy.md](../../docs/listing-quota-policy.md).

Запуск из корня проекта:

```sh
node integrations/listing-quotas/adapter.test.cjs
node tests/seller-listing-quotas.cjs
```

## Демо-форма и автоматический повтор

Общий скрипт должен загружаться **до основного inline-скрипта и первого `autoRelistEnded`**, а не только перед `seller-ui.js`. Это нужно для квоты автоматического повтора при первом открытии страницы. В рабочем HTML скрипт подключает владелец основного выпуска; этот изолированный патч намеренно не правит index/sw.

`privateQuotaIssue` в `seller-ui.js` вызывает `localChangeDecision` после последнего чтения медиа, непосредственно перед записью публикации; при отказе сохраняет черновик и оставляет форму открытой. Возобновление проверяется отдельно. При вводе в редакторе показывается статичная подсказка; каталог не сканируется на каждом нажатии клавиши. Точный `localUsage` считается при открытии кабинета и применении увеличивающего квоту действия. Предпросмотр платного тарифа не участвует в этих решениях.

`guardLocalRenewalPlan` проверяет уже подготовленный план `FasAuctionRenewal.plan`: один проход считает занятые места затронутых владельцев, затем разрешённые повторы последовательно резервируют их. Два завершённых лота не занимают одно последнее место одновременно. Банк/seed без `sellerOwnerId` сохраняет прежнее поведение. Если общего модуля нет, частные автоматические повторы блокируются, а банковские остаются доступны. История ставок, цены, сроки существующих защищённых торгов и opt-in правила не переписываются.

В VM fixtures добавлена только загрузка новой зависимости; диагностический `SOURCE_FILES` теперь включает её для проверки неизменности кода. Никакая заглушка не выдаёт платные права и не отключает квоту.

## Вход координатора

```js
const { createListingQuotaCoordinator } = require('./adapter.cjs');
const coordinator = createListingQuotaCoordinator({
  // Оставить disabled до реализации всех требований ниже.
  configuration: { state: 'disabled' },
  authorize: trustedServerAuthorization,
  repository: durableQuotaRepository
});
// Реальный запрос получит integration-disabled, пока подключение не проверено.
await coordinator.apply({
  version: 1,
  idempotencyKey: 'unique-command-key-0001',
  listingId: 'listing-123',
  expectedListingRevision: 7,
  preparedChangeId: 'server-prepared-change-456'
}, authenticatedServerRequestContext);
```

Нельзя заменять `authorize` чтением локального `sellerOwnerId`, выбранного demo-тарифа, `tenantId` из тела запроса или пользовательского HTTP-заголовка. Авторизация возвращает проверенный `principalId` и область `{kind:'private'|'organization', id}`. Сотрудники одного банка используют общий организационный лимит; личность сотрудника остаётся отдельной для журнала и ключей повторного запроса.

## Обязательный контракт repository

`withQuotaTransaction(scope, callback)` должен выполнять callback **в одной постоянной сериализуемой транзакции**, блокируя область, политику и затронутый лот. Нельзя реализовывать его production-версией тестового JS mutex, отдельными несогласованными чтениями/записями или проверкой числа карточек в браузере. Транзакция полностью откатывается при исключении, в том числе после неудачного `completeCommand`.

| Метод внутри транзакции | Обязательство |
| --- | --- |
| `claimCommand({principalId,scope,idempotencyKey,fingerprint})` | Постоянная уникальность по principal+scope+key. Возвращает `new` либо ранее `complete`, с теми же scope/principal/fingerprint; иной fingerprint — конфликт. Успешный повтор возвращает прежний разрешённый результат без второго резервирования |
| `getListing(listingId)` | Канонический лот или `null`, включая scope, ревизию, canonical `categoryId`, статус, принятые ставки и защищённые сроки |
| `getPreparedChange(...)` | Неизменяемое, ещё действующее подготовленное изменение для этого principal/scope/лота/ревизии: `{principalId,scope,listingId,expectedListingRevision,expiresAt,next}`. Идентификатор не переиспользуется с другим содержимым. Payload проверен и сохранён сервером; срок нельзя принимать из тела пользователя |
| `validateAuctionChange({principalId,scope,before,next,now})` | Подтверждает **актуальные** полномочия и права на предмет, допустимость публикации, неизменность предмета/цены/условий после ставки и допустимость перехода. Использует тот же журнал/блокировки, что приём ставки, отзыв/пауза и завершение. Возвращает строго `true` |
| `getEntitlement(scope)` | Администраторская/банковская каноническая запись. Для free-private — `null`, для организаций без договора — отказ. Флаг оплаты из браузера и return URL не предоставляют тариф |
| `getUsage(scope,now)` | `{revision,counts}` из постоянных резервов с учётом истёкших защищённых сроков. Сумма четырёх корзин равна `total`. Ревизия и счётчики согласованы внутри этой транзакции |
| `commitChange(...)` | Атомарно меняет лот, резервы и usage-ревизию с CAS ожидаемых ревизий. Сверяет актуальность policy revision. Возвращает следующую `listingRevision` и `usageRevision`; никакого отдельного commit до конца транзакции |
| `completeCommand(...)` | Сохраняет разрешённый результат и fingerprint в той же транзакции, возвращает `true`. Ошибка откатывает публикацию и резерв |

`claimCommand` не является отдельным сетевым lock. После успешной транзакции результат повторяем; для отклонённого/откаченного запроса долговременная фиксация отказа не обещается. После изменения условий клиент создаёт новую команду с новым ключом.

Только одна запись с одним и тем же `listingId` может владеть резервом. Переход между организациями не поддерживается этим координатором: для него нужна отдельная проверенная операция с блокировками **обеих** областей. Действия победы/продажи/окончания торгов и продления используют тот же реестр резервов и атомарные блокировки, но не выдаются за пользовательское изменение объявления через `preparedChangeId`.

Ошибки авторизации/БД наружу преобразуются в короткие коды. Не добавляйте в HTTP-ответы, метрики или уведомления токены, DSN, платёжные данные и полные записи repository.
